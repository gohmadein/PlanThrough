PlanThrough 项目智能体接手说明
==============================

用途
----
这份文件是给后续接手本项目的 AI 智能体阅读的技术交接文档。

在修改任何代码之前，请先完整阅读本文件、README.md 和 PRODUCT_SPEC.md，再检查当前 Git 状态和实际代码。不要只根据文件名猜测行为，也不要推翻现有架构重新生成项目。


一、项目定位
------------
PlanThrough 是一个把甘特图、思维导图式递归展开、流程连线、进度归并和节点审批结合在同一张二维画布中的项目设计与执行工具。

一句话定义：
“甘特图上叠加思维导图的展开与收敛能力，思维导图中植入时间轴与进度归并逻辑。一张图，无限穿透。”

核心视觉：
1. 横轴代表时间。
2. 纵向区域代表事件分类，默认是 Thinking、Doing、Acting，项目内可以自定义。
3. 一级、二级、三级节点可以递归展开。
4. 节点宽度必须对应真实工期，不应为了容纳按钮而强行拉宽。
5. 父节点展开后，子节点显示在半透明框中，并拥有更细的局部时间刻度。
6. 时间重叠会产生黄色并发时间线。
7. 逻辑线决定执行顺序，关系线只表达关联。

当前公开体验版：
https://planthrough-workflow.lmx71017.chatgpt.site

当前界面版本：
公测版 v0.3.0


二、技术栈和运行方式
--------------------
主要技术：
- TypeScript
- React 19
- Next.js App Router 结构
- vinext + Vite
- Cloudflare Worker
- Cloudflare D1：保存公开体验反馈
- Cloudflare R2：保存反馈截图
- Drizzle ORM / Drizzle Kit：数据库结构与迁移
- localStorage：保存用户在浏览器中创建的项目
- IndexedDB：保存用户上传到节点的附件

环境要求：
- Node.js 22.13.0 或更高版本
- npm

本地启动：
1. npm install
2. npm run dev
3. 浏览器打开 http://localhost:3000

完整检查：
1. npm run lint
2. npm test
3. git diff --check

生产构建：
1. npm run build
2. npm run start

数据库结构变化后：
1. 修改 db/schema.ts
2. 执行 npm run db:generate
3. 检查新生成的 drizzle/*.sql
4. 再执行 npm test

五、核心数据模型
----------------
Project：
- version：当前为 2
- id、name
- start、end
- createdAt、updatedAt
- status：draft / running / paused / completed
- timelineVisible：是否显示并发时间线
- categories：事件分类
- nodes：全部节点，使用扁平数组保存
- links：全部逻辑线和关系线
- attachments：节点附件的元数据，不包含文件二进制

PlanNode：
- id
- parentId：null 表示一级节点，否则指向父节点
- title
- categoryId
- start、end
- progress
- weight
- status：pending / active / completed
- working：执行原则、执行内容、验收标准、团队、审批流和结果

PlanLink：
- id
- kind：logic 或 relation
- from、to

特殊连接点：
- START_ID = "__project_start__"
- END_ID = "__project_end__"

起点和终点不是普通 PlanNode，但可以作为逻辑线的 from/to。
启动项目必须存在：
起点 → 一级节点逻辑路径 → 终点

不要重新加入起点与终点之间的装饰性水平直线。画布中只应显示用户真正创建的逻辑线和关系线。


六、项目和附件的保存方式
------------------------
用户创建的项目：
- localStorage key：planthrough-projects-v2
- 当前项目 key：planthrough-current-v2

节点附件：
- IndexedDB 数据库：planthrough-files-v2
- 附件文件只存在当前浏览器设备

重要结论：
1. 不同用户和不同浏览器不会自动共享项目。
2. 清理浏览器数据可能丢失项目和附件。
3. 项目 JSON 导出包含结构和附件元数据，不包含附件二进制。
4. GitHub 源码和公开网页不会保存用户的项目内容。
5. 公开反馈是唯一当前会保存到云端 D1/R2 的用户提交内容。
6. 未经用户明确允许，不要把项目数据、节点内容或附件发送到反馈 API。


七、节点层级和编号
------------------
节点采用扁平数组 + parentId 表达树结构。

重要函数：
- childrenOf()：取得直接子节点
- descendants()：取得全部后代
- nodeDepth()：计算节点层级
- sortedSiblings()：同父节点按开始时间排序
- displayNumber()：根据排序生成 A1、A1-B1、A1-B1-C1

节点时间拖动后，编号应立即按时间重新排序。
删除节点后也要重新体现正确编号。

默认只正式支持三级：
- level 0：一级节点
- level 1：二级节点
- level 2：三级节点

一级和二级节点即使没有子节点，也允许点击展开框，以便用户在框中添加后续子节点。


八、时间和布局逻辑
------------------
默认新项目：
- 开始日期是当天
- 结束日期是开始日期后 1 年
- 默认分类 Thinking、Doing、Acting

时间包含原则：
- 子节点开始、结束时间必须完全落在父节点时间范围内
- 项目周期必须包含所有一级和下级节点

节点宽度原则：
- 节点宽度代表真实工期
- 不能用固定最小宽度掩盖工期差异
- 工期过短时，先隐藏名称或次要信息
- 再不够时节点纵向增高，W、聚焦、展开按钮上下排列

layout useMemo 是布局核心。
其中包含：
- nodeMetrics()：根据日期宽度和层级计算节点宽高
- rowOffset()：同分类节点交错排布
- measureBand()：递归测量分类区域高度
- measureFrame()：递归测量子节点框
- placeFrame()：放置局部框、局部分类和局部时间轴

修改 layout 前要理解完整递归关系。不要只修一个坐标常量，否则容易出现：
- 二级框没有跟三级框一起增高
- 节点压在父节点或兄弟节点上
- 局部时间轴与全局日期不对应
- Thinking / Doing / Acting 分类标签位置错误

全局和局部时间轴必须使用同一日期映射，只是刻度粒度不同。


九、连线逻辑
------------
逻辑线：
- 决定执行顺序
- 参与节点解锁
- 参与项目启动有效通路判断
- 使用深蓝实线和箭头

关系线：
- 只表示关联
- 不参与执行顺序、进度和解锁
- 使用紫色虚线和箭头

连线通常限制在同一父节点下的同级节点之间。
起点和终点只参与一级逻辑流程。

重要函数：
- logicEntries()：某一层级没有逻辑前置的入口
- logicExits()：某一层级没有逻辑后继的出口
- hasStartToEndPath()：验证起点到终点有效通路
- predecessorComplete()：判断所有逻辑前置是否完成
- visibleEntryIds() / visibleExitIds()：展开节点后，把外部逻辑线动态连接到可见的最深层入口/出口
- bezier()：绘制曲线路径

节点展开时：
- 如果父节点有可见子节点，外部逻辑线应改接子层入口或出口
- 展开三级时同理递归穿透

同两个节点同时存在逻辑线和关系线时，两条线需要错开，不能完全重合。

删除模式：
- 只允许删除逻辑线和关系线
- 并发时间线、当前日期线、分类分割线不能删除


十、并发时间线
--------------
时间重叠检测在 concurrency useMemo 中完成。

当前只保留真正的并发竖向黄色虚线。
不要恢复“每个节点开始日期和结束日期都画一根黄色线”的旧行为。

并发线贯穿画布纵向区域，鼠标悬停显示解释。
当前日期线是红色，不属于并发线。


十一、进度、状态和执行顺序
--------------------------
项目状态：
- draft：设计中
- running：执行中
- paused：暂停，可重新调整结构和时间
- completed：完成

节点状态：
- pending：未执行
- active：当前执行
- completed：已完成

项目未开始时：
- 节点不灰度
- 三个状态灯全部熄灭

项目启动后：
- 未执行：红灯
- 当前任务：黄灯
- 已完成：绿灯

重要函数：
- calculatedProgress()：子节点按权重归并到父节点
- isPendingExecutable()：判断节点是否已满足执行条件
- nodeTone()：决定节点当前视觉状态
- terminalRoots()：寻找一级逻辑流程末端节点
- allTerminalRootsComplete()：决定终点是否可点击
- canEdit()：决定结构和时间是否可修改

启动项目：
1. 必须存在起点到终点的完整逻辑通路。
2. 起点点击后，入口一级节点和其可执行下级节点被激活。
3. 没有完整通路时必须阻止启动并提示用户。

完成节点：
1. 当前节点按 Working 规则验收。
2. 通过后进度为 100%。
3. 后继节点只有在所有前置节点完成后才解锁。
4. 深层节点状态向父级归并。

完成项目：
1. 所有末端一级逻辑节点完成。
2. 用户点击终点。
3. 项目变为 completed，终点变绿并显示完成动画。


十二、Working 面板
-----------------
WorkingPanel 位于 PlanTool.tsx。

主要内容：
1. 节点名称、分类、权重和日期
2. 自身进度
3. 节点执行原则
4. 节点执行内容
5. 验收标准
6. 执行团队
7. 审批流及成果提交
8. 执行结果
9. 节点连接关系

审批流规则：
- 第一步是发起人
- 最后一步是审定人
- 新增审批步骤只能插入两者之间
- 每一步都有人员、说明、上传附件和动作按钮
- 执行结果区域中，“验收通过”在上方
- “不通过”和理由在下方

鼠标悬停节点会显示审批摘要，不需要打开 Working 面板。


十三、公开体验反馈系统
----------------------
反馈入口：
- 左侧项目工作台右下角“意见反馈”

反馈提交内容：
- 类型
- 问题描述
- 期望效果
- 联系方式（可选）
- 截图（可选，最大 5MB）
- 自动附带项目名称、版本、当前 URL、浏览器和窗口尺寸

明确不会自动提交：
- 节点内容
- 项目 JSON
- 本地节点附件

云端绑定：
- D1：DB
- R2：FEEDBACK_FILES
- 管理员口令环境变量：FEEDBACK_ADMIN_KEY

安全要求：
1. 绝对不要把 FEEDBACK_ADMIN_KEY 写进代码、README 或提交记录。
2. 不要让 GET /api/feedback 变成公开接口。
3. 不要让截图 R2 对象直接公开。
4. 所有截图读取都必须再次校验管理员口令。
5. 对公开文本做长度限制，对图片做类型和大小限制。
6. 如果新增删除反馈功能，也必须通过管理员验证。


十四、样式修改注意事项
----------------------
优先把新增样式写入 app/extras.css。

不要轻易整体重写 app/globals.css，因为它是压缩单行历史文件。

修改节点视觉时同时检查：
- regular
- compact
- narrow
- 一级、二级、三级颜色
- 未开始、当前、完成状态
- 展开框
- 100%、低倍缩放和高倍缩放

修改侧栏时同时检查：
- 只打开项目工作台
- 同时打开 Working 面板
- 工作台收起
- 页面窄屏

时间轴位于画布下方并随可视区域悬浮。
缩放较大时，悬浮时间轴会切换到更低层级的局部时间轴；缩小时回到全局时间轴。


十五、测试和验证
----------------
tests/rendered-html.test.mjs 会验证：
- 页面和路由存在
- 主要产品文案和功能标识存在
- 默认一年周期
- 不存在旧的节点时间竖线
- 不存在起点终点装饰性水平线
- 帮助和反馈功能存在
- D1/R2 绑定和反馈表存在

每次修改后至少执行：
npm run lint
npm test
git diff --check

如果修改了交互或布局，还要启动 npm run dev 并实际打开页面检查。

如果 npm test 与正在运行的开发服务器争用 dist 构建目录：
1. 暂停本地开发服务器。
2. 执行 npm test。
3. 测试结束后重新执行 npm run dev。

不要为了让测试通过而删除有效断言。应修复实际代码，或者在架构确实变化时同步更新测试。


十六、部署注意事项
------------------
本项目包含 .openai/hosting.json，表示它已经连接到一个现有 Sites 项目。

部署时必须：
1. 保留现有 project_id。
2. 保留 D1 和 R2 逻辑绑定。
3. 确保 drizzle 迁移包含在发布包中。
4. 在生产环境设置 FEEDBACK_ADMIN_KEY，且标记为 secret。
5. 先完成 npm test。
6. 保存新版本后再部署。
7. 公开体验站点的访问模式应为 public。
8. 发布后验证首页、/feedback 和受保护的反馈 API。

公开地址：
https://planthrough-workflow.lmx71017.chatgpt.site

如果伙伴无权访问原 Sites 项目：
- 不要擅自替换这个 project_id 后覆盖原站点。
- 可以本地开发，或者在得到项目所有者允许后新建自己的独立部署。


十七、Git 和文件操作原则
------------------------
1. 修改前执行 git status -sb。
2. 不要覆盖用户已有的未提交修改。
3. 不要使用 git reset --hard。
4. 不要用 git checkout -- 丢弃文件。
5. 不要无目的地格式化整个项目。
6. 提交前检查 git diff 和 git diff --check。
7. 只提交与当前需求有关的文件。
8. dist、node_modules、.next 和本地 Wrangler 状态不应加入版本控制。
9. 管理员口令、访问令牌和部署凭证绝不能写入 Git。


十八、智能体推荐工作流程
------------------------
收到修改需求后按以下顺序执行：

第一步：理解需求
- 先复述需求对应的用户流程。
- 判断是修改设计阶段、执行阶段、数据保存、反馈系统还是部署。

第二步：定位代码
- 优先使用 rg 搜索界面文字、className、函数名和数据字段。
- 不要一开始读取或重写整个 PlanTool.tsx。

十九、常见错误和禁止回归
------------------------
后续修改时不要让以下问题重新出现：

1. 起点和终点之间出现一条装饰性横线。
2. 每个节点开始、结束日期都出现黄色竖线。
3. 节点宽度与工期无关。
4. 工期短时节点内容和按钮互相覆盖。
5. 项目未开始时红灯亮起。
6. 未执行节点整体灰度显示。
7. 展开三级后，二级框没有跟着增高。
8. 局部时间轴与全局日期位置不对应。
9. 父子线穿过节点。
10. 逻辑线和关系线重合。
11. 展开父节点后外部逻辑线仍连接折叠父节点，而没有连接可见子层入口/出口。
12. 起点或终点没有接入逻辑线却允许项目启动。
13. 未完成末端逻辑节点却允许点击终点。
14. 关系线参与节点解锁。
15. 浏览器本地项目被误上传到服务器。
16. 管理员反馈口令出现在前端代码或 Git 中。
